# 프로토타입 테스트 안내

최신 검증은 아래 [1층 엘리트 4종과 구행 보스](#1층-엘리트-4종과-구행-보스--2026-10-23) 절을 참고하세요. 이전 절의 기보 경로·명령 수·저장 버전은 당시 기록입니다.

2026-10-23 1차 폴리싱 후 Rust 35개·브라우저 7개를 검증했습니다. 추가한 행마·부활 회귀 2개와 보드 기반 휴식 E2E 2개의 목적·방식·실행 방법은 [폴리싱 검증](POLISHING.md#검증)에 있습니다. 아래 프로토타입/콘텐츠 분리 기록은 이전 작업의 검증 내역입니다.

테스트는 실제 플레이에 영향을 주는 연결 지점에 집중했습니다. 함수별 테스트를 추가하지 않았습니다. **기존 23개 중 제거된 `RuleModule` 연결 테스트 1개를 정리하고 나머지 22개를 유지**, 첫 프로토타입의 핵심 Rust 시나리오 8개를 유지했습니다. 이번 분기 맵 변경에서는 Rust 맵 시나리오 2개를 추가하고 기존 완주 테스트를 새 경로로 갱신했습니다. 브라우저 테스트는 총 5개입니다. 정식 UI에는 테스트 전용 몬스터 선택·상태 변경 도구가 없습니다.

## 실행 순서

저장소 루트에서 아래 순서로 실행합니다. 최초에는 README의 개발 환경 준비와 `npm ci --prefix web`을 완료하세요.

```sh
# 1. 소스 형식과 정적 검사
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings

# 2. 네이티브 Rust 규칙과 원정 연결
cargo test --workspace

# 3. 브라우저용 컴파일과 실제 WASM 생성
cargo check --workspace --target wasm32-unknown-unknown
npm run wasm --prefix web

# 4. TypeScript 검사 및 프로덕션 번들
npm run build --prefix web

# 5. 첫 실행에서만 브라우저 설치 (네트워크 필요)
cd web
npx playwright install chromium
npm run test:e2e
```

설치된 Chrome을 사용할 때는 브라우저 다운로드 대신 다음과 같이 실행할 수 있습니다.

```sh
CHESSLAYER_CHROME=/usr/bin/google-chrome npm run test:e2e --prefix web
```

Playwright가 `127.0.0.1:5173`의 Vite 서버를 자동으로 시작합니다. 해당 포트에서 이 프로젝트가 실행 중이면 재사용합니다. 다른 앱이 같은 포트를 사용하고 있으면 먼저 정리해야 합니다. 네트워크 격리 환경에서는 localhost와 브라우저 실행 권한이 필요합니다. 이 작업 환경에서는 해당 실행 권한을 사용했습니다.

Rust만 빨리 다시 검증하려면 `cargo test -p chesslayer --test prototype`을 실행합니다. 개별 테스트 이름을 명령 끝에 붙이면 해당 시나리오만 실행합니다. Rust 테스트는 독립적이므로 실행 순서에 의존하지 않으며 기본적으로 병렬 실행합니다. 브라우저 테스트는 1 worker로 파일 순서대로 실행하고 매번 새 페이지와 새 원정을 사용합니다.

## 그래프형 강화 트리 UI — 2026-10-23

휴식 강화 화면을 실제 `upgrade_paths`로 생성하는 노드·연결선 그래프로 교체했다. Rust 강화 정의, 비용, 선행 조건, 명령 및 저장 형식은 변경하지 않았다. 현재 콘텐츠는 일반 기물에서 갈라지는 9개 경로이며 후속 단계는 아직 없다. UI를 채우기 위한 강화는 추가하지 않았다.

`web/src/upgradeTree.ts`는 현재 기물이 속한 연결 성분 전체(기본 기물·형제 분기·선조·후손)를 수집한다. 선행 순서에 따라 깊이를 배정하고 같은 단계의 노드를 떨어뜨려 배치한다. 여러 부모가 있는 목적지는 하나의 노드로 합치고, 긴 연결에는 보이지 않는 경유 공간을 예약한다. 여러 선행 관계를 연결선으로 표시하되, 현재 엔진의 `from → to`는 각각 선택 가능한 전환 경로이므로 이를 임의의 AND 조건으로 바꾸지 않는다. 조건 문구도 원본을 표시한다.

획득 경로는 기존 저장 명령의 `rest_upgrade` 기록으로 판단한다. 전투 승격으로 현재 종류가 바뀌었다는 이유만으로 일반 기물에서 그 종류로의 쉼터 강화를 획득했다고 표시하지 않는다. 강화 확정 시 기존 엔진은 즉시 행동을 소비하고 맵 단계로 이동·저장한다. UI만 갱신된 트리를 남겨 성공한 경로를 보여주며, 맵으로 돌아가기·닫기·Esc로 결과 화면을 닫는다. 재확정 버튼은 사라지고 새로고침하면 정상 맵을 복원한다.

### 기보 변경 이유와 현재 경로

기존 `왕관의 근위대`의 이동·포획을 전제로 했던 수는 새 편성에서 불법이거나 다른 결과를 만들었다. 임시 로컬 도구로 정상 `Game::dispatch`와 공통 AI를 재생해 명령 기록만 갱신했다. 준비 도구는 저장소/제품에 포함하지 않았다. `losing-run.json`은 일반전에서 끝나므로 변경하지 않았다.

- `winning-run.json`: 28명령. 이동 13회, 카드 사용 2회, 카드 보상 3회, 보물 2회, 강화 1회, 노드 선택 7회. 경로는 기존과 같은 `2→6→8→10→14→17→18`, 즉 일반전→보물→마하라자→쉼터→호드→보물→구행이다. 새 적의 정상 행동을 거쳐 킹으로 구행을 직접 포획한다.
- `tempest-promotion.json`, `bouncing-promotion.json`: 각각 28명령. 같은 마하라자 승리 후 쉼터 10에서 a2 폰을 강화한다. 이후 일반전 13(쌍둥이 주교)에서 a8 승격, 해당 계열 퀸으로 실제 이동 및 적 로얄 포획을 수행하고 보상 후 다음 일반전 15까지 진형을 계승한다. 기존처럼 다음 전투 진입·저장 복원을 검사하며 보스 완주는 별도의 승리 기보가 담당한다.
- `rest.spec.ts`, `variants.rs`: 현재 쉼터의 킹 f1·비숍 c5·퀸 d1 위치를 반영한다. 강화 후 위치 계승 검사는 노드 13으로 진행한다. 노드 14의 새 호드는 c5도 점유하므로 그 경로에서는 기존 역습 규칙상 비숍이 사망하는 것이 정상이다. 해당 충돌은 완주 기보에 남겨 검증한다.
- 모바일 부활 테스트는 같은 명령 경로에서 첫 엘리트 이동 직전 청바지를 실제 사용한다. 원래의 퀸 이동 대체는 더 이상 필요 없어 제거했다.
- 소용돌이 회귀는 고정된 옛 인덱스 5 대신 생성된 맵의 여러 기물 엘리트를 찾아 실제 원본 편성과 섞인 위치를 비교한다.

### 저장 기록 호환성

저장은 `character + seed + commands`를 처음부터 재생한다. 엘리트와 보스가 바뀌면 과거 명령의 합법성뿐 아니라 AI·카드 난수 진행과 보드 결과도 달라질 수 있으므로 버전 2를 자동 재생하지 않는다. 새 버전은 **3**이다. localStorage 키는 `chesslayer.run.v1` 그대로 유지하여 이전 기록을 읽고 설명할 수 있다. 이전 저장은 사용자가 새 원정을 시작하기 전까지 보존되며 자동 이관은 없다. 버전 1도 같은 방식으로 안내한다.

### 실행 방법과 확인 결과

저장소 루트에서 실행한다. 런타임·의존성 준비는 이 문서 앞의 실행 순서를 따른다.

```sh
# 새 편성과 구행, 지도 연결만 빠르게 확인
cargo test -p chesslayer --test encounters --test act_map --test content

# 전체 Rust 및 WASM 검사
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo check --workspace --target wasm32-unknown-unknown

# 기존 환경에 설치된 동일 버전 바인딩 CLI 사용
cargo build -p chesslayer-web --target wasm32-unknown-unknown --release
/tmp/chesslayer-tools/bin/wasm-bindgen --target web --out-dir web/src/wasm \
  target/wasm32-unknown-unknown/release/chesslayer_web.wasm
npm run build --prefix web

# 실제 WASM/React와 저장 기록 검증
CHESSLAYER_CHROME=/usr/bin/google-chrome npm run test:e2e --prefix web
git diff --check
```

다른 개발 환경에서는 `npm run wasm --prefix web`으로 동일한 WASM을 생성할 수 있다. 이 환경은 앞 절에 기록된 wasm-pack 캐시 제약을 피해 이미 설치된 wasm-bindgen을 사용했다. Chrome 실행은 localhost 서버와 브라우저 실행이 허용되는 환경이 필요하다.

검증 결과: **Rust 43개, Playwright 12개(실제 Chrome 11개 + 트리 배치 1개) 모두 통과**. fmt, Clippy, wasm32 검사, release WASM 바인딩 생성, TypeScript/Vite 프로덕션 빌드도 통과했다. 전체 브라우저 실행은 약 1분 12초였다. 신규 Rust 시나리오는 3개이며 브라우저 테스트 수는 늘리지 않았다. 지도와 완주 화면 스크린샷을 직접 확인했으며, 승리 문구에서 발견한 옛 보스 이름은 현재 전투명을 표시하도록 수정한 뒤 빌드와 완주 E2E를 재검증했다.

확인 범위 밖: 건어물·런던은 정확한 배치와 시드 출현을 Rust에서 검증했지만 각각을 상대로 한 브라우저 완주 기보는 추가하지 않았다. 모든 시드·캐릭터의 난이도 균형과 장기 플레이는 평가하지 않았다. 구행 이미지는 후속 요청으로 지정된 decoded-svg/149 원본을 사용한다. 아군은 위, 적군은 아래를 향하며 색은 동일하다. 원본과 변환은 [ASSETS.md](ASSETS.md)에 기록했다.


### 구행 원본 SVG 적용 후속 검증

사용자가 지정한 decoded-svg/149 구행 SVG로 임시 룩을 교체했다. 원본에 포함된 그림과 색을 유지하고, 아군용은 위를 향하게, 적군용은 180도 회전하여 아래를 향하게 했다. 같은 45×45 프레임과 크기를 사용한다.

`cargo test -p chesslayer --test content`로 양 진영 에셋 등록을 확인하고 `npm run build --prefix web`으로 실제 번들을 생성한다. 기존 완주 E2E는 구행 보스의 SVG 로딩과 초기 배치 화면도 확인한다. 같은 원본의 양 진영 비교 화면과 실제 보스 화면을 열어 방향·글자 회전·색·잘림 여부를 확인한다. 새 테스트나 디버그 UI는 추가하지 않는다.

후속 실행 결과: 콘텐츠 등록 Rust 테스트, TypeScript/Vite 빌드, 실제 Chrome 완주 E2E와 `git diff --check` 모두 통과했다. 양 진영 SVG의 내부 그림이 같고 바깥 변환만 0도/180도인지 XML로 확인했다. 비교 렌더와 `web/test-results/hook-boss.png`를 직접 열어 아군 위·적군 아래 방향, 같은 색, 반사되지 않은 글자와 보드 안의 정상 표시를 확인했다.
